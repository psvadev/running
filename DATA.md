# DATA.md — data semantics for puls.json

Field dictionary and caveats for the session data. Purpose: let any future session (human, Claude, or an AI chat fed the TSV export) reason correctly about this data without rediscovering its assumptions. Short and factual — architecture/dev context lives in HANDOFF.md (local).

## Session fields

A trailing **`?`** on a type marks an **optional** field — the key may be absent from a session's JSON (each row notes what "absent" means, e.g. `land` absent = home country). Types without `?` are present on every session.

| Field | Type | Semantics & caveats |
|---|---|---|
| `id` | string | Stable unique id; edits reuse it. |
| `dato` | `YYYY-MM-DD` | Local date (not UTC) — see `localISODate` helpers. |
| `uke` | `YYYY-WW` | ISO week, derived from `dato`. |
| `oktnavn` | string | Free text; often auto-generated as "{Treningsplan} {Økttype}". **A `Race` is the exception** — it takes the title of the 🏁 event on that exact date ("Berlin Marathon"), and with no event registered the field is left blank rather than named after a programme that never prescribed it. Only ever overwrites a name the app itself generated. |
| `okttype` | string | One of the 7 core types (Easy, Steady, Long, Tempo, Intervaller, Test, Race) or a user-defined custom type. Only **Test/Race** anchor the Prognose (outdoor ones only) and Formkurve. |
| `treningsplan` | string | Egentrening, Runna, or custom. Defaults to Runna, except for a **`Race`**, where it is derived: a race closing a training block was prescribed by that block, so it keeps the plan; a race outside every Plan-event window was prescribed by nobody → **Egentrening**. One-directional — when a block *does* cover the date the field is left alone rather than guessing a dropdown value from the event's free-text title. A hand-pick sets `Form.planTouched` and is final for that form. |
| `varighet` | seconds | **Normally the sum of the five zone times** ("auto fra soner"). **Strava-imported sessions store Strava's `moving_time` instead**, which can differ slightly from the zone sum. Manually entered when "Uten pulsdata" is checked. |
| `distanse` | km (float) | Treadmill: belt-measured. Outdoor: GPS. These disagree systematically — see "Belt vs GPS" below. |
| `gjsnittspuls` / `toppuls` | bpm | Missing on some sessions. Known anomalies: **2026-06-24 HR is estimated from Apple Health** (not chest strap); **2026-04-17 and 2026-07-01 have no pulsdata at all**. Sessions without HR contribute **zero** to the zone-weighted load, PMC (CTL/ATL/TSB), and Belastning charts. |
| `soner` | `[s1..s5]` seconds | Time per pulse zone. Zone boundaries use **touching convention** (zone N max = zone N+1 min), matching Strava. |
| `kalorier` | int | From watch/Strava; not used in any computation. |
| `malDistanse` | km | The planned distance for the session. |
| `tempo` | sec/km | Auto-calculated from varighet/distanse. |
| `snittkmh` | km/h | Auto-calculated; feeds aerobic efficiency (`snittkmh / gjsnittspuls × 100`). |
| `stigning` | % (≤20) | **Treadmill incline only.** Usually 1 % — the standard outdoor-equivalence convention, so treadmill paces are already roughly outdoor-equivalent in energy cost. Not an elevation measurement. |
| `hoydeMeter` | m | **Outdoor elevation gain only** (mutually exclusive with `stigning`). Per-run totals are too coarse for grade-adjusted pace — do not attempt GAP from this. |

> **The `stigning` / `hoydeMeter` exclusivity is enforced on save (2026-08-06), not just in the form.** `Form.read()` nulls whichever field the session's venue doesn't own. Until then the venue change only *hid* the other field and never emptied it, while `clear()` seeded Stigning with the 1 % default before the venue was settled — so logging an outdoor run right after a treadmill one wrote a phantom `stigning: 1` onto it. **Sessions saved before that date may still carry it**; it renders as "Stigning 1 %" in the detail panel and fills the log's Høyde column when there's no `hoydeMeter`. No chart or record reads `stigning`, so nothing downstream is affected. The form-side rule now lives in one place, `Form.syncVenueFields()`.
| `sko` | string | Shoe name; km per shoe aggregated for lifecycle tracking. |
| `løpetype` | `utendors` \| `treadmill` | Venue. Default `utendors`. |
| `sovn` | hours (decimal)? | **Retired 2026-07-20** — no longer collected, surfaced, or exported. Present only in historical sessions logged before that date. Was "sleep the single night before the run" (6.87 = 6 h 52 m); dropped because a single night can only capture acute effects (physiologically weak) while chronic sleep debt was never in the data — sparse and uncharted, so not worth the logging friction. Old values stay in the JSON, harmless. |
| `rpe` | 1–10 | Apple Fitness scale. **The field was added 2026-06-01; values before that (back to late April 2026) were backfilled from Apple Fitness** — contemporaneous recordings, not reconstructed memory. Sparse before late April 2026. |
| `beskrivelse` | string | Workout structure; auto-filled from Strava (Runna pushes its program text into Strava's description). |
| `notater` | string | Free-text session notes; carries the "why" for flagged sessions. |
| `utenforAnalyse` | bool? | Outlier flag ("Avvik"). `true` = excluded from **quality** analytics (trends, insights, quality charts, pace/distance records, Prognose/Formkurve anchors) but **kept** in all volume metrics (km totals, streaks, heatmap, load, PMC, blocks, goals). Absent = false. Exclusions are always visible (dimmed log row, detail-panel row, `[Avvik]` tag in exports). |
| `land` | ISO 3166-1 alpha-2? | Country the run took place in. **Absent/empty = Norway** (home default) — only filled for abroad runs. TSV exports the raw code (e.g. `SE`). Norwegian display names are derived at runtime via `Intl.DisplayNames`; unresolvable typed text is stored raw and shown without a flag. Not used in any computation — powers only the "Land løpt i" card. **Strava auto-fill:** `location_country` is Strava-deprecated (usually null), so import falls back to the activity **timezone** (`Asia/Manila` → PH) via a bundled tz-database zone→country lookup. **Abroad only** — a resolved `NO` (home) is deliberately left blank to keep the "empty = Norge" convention; unknown zone → blank too (never a wrong guess). |
| `stravaId` | string? | The Strava activity id this session was filled from. Set on sessions populated via "Hent fra Strava" **from 2026-07 onward** — older and manually-entered sessions start with none, but can be **retro-linked** in one pass via **Innstillinger → Koble gamle økter til Strava** (matches history by date + venue + distance/duration, unique + user-approved). Enables the edit-form "Oppdater fra Strava" button (re-pull the same activity by id) and unlocks the Strava-stream analyses (run/walk, HR-drift, kadens) for that session. **Internal handle only** — not used in any computation and never shown in the log, session detail, or TSV export (lives in `puls.json` and a hidden form field). |
| `stravaAnalysis.continuity` | object? | **Derived Run/walk ratio estimate** for an outdoor Strava run (absent otherwise). Auto-computed from the activity's per-second speed stream: running-vs-walking share (`runningRatio`/`walkingRatio`/`unclassifiedRatio`, over moving time), longest unbroken run, run→walk transitions, experimental uphill walking, and `datakvalitet` (høy/middels/lav). **Estimate, not truth** — walking and easy jogging overlap on speed, so treat it as a *trend*, not exact minutes. Speed thresholds come from `continuitySettings` (default 7.0 / 7.5 km/h); the result is version- and threshold-stamped, so it's re-computed when the algorithm or the thresholds change. **Version 2 made recording gaps count as stopped** — it was the last of the three analyses still deciding "stopped" from Strava's `moving` flag alone, the flag proven blind to real pauses (see the `splits` row for the full shape). Worse than merely missing them: an unflagged gap fell through to the smoothed speed of the samples *either side* of it, which is normal running speed, so **a three-minute stop at a crossing was counted as RUN** — inflating both running time and Løping% on any outdoor run with a stop. In the synthetic regression a 181 s standstill inside two 60 s runs reported **300 s of running**; it now reports 119 s of running and 181 s stopped. The test is the shared `isStoppedInterval` (covered < 0.5 m/s), but **only on intervals longer than `GAP_MIN_SECONDS` (5 s)** — a stopped segment is deliberately never cleaned up as noise, so a single flat GPS second would otherwise chop a continuous run in two, while legitimately sparse sampling (Strava smart recording, ~10 s apart) survives the conjunction because the speed across it is normal running speed. Moving-time accounting applies the same predicate *without* the duration gate, which is what reproduces Strava's `moving_time` — the two callers differ on purpose. **Version 3, the same day, closed the other half: a stop must also have covered no ground.** The first backfill exposed it — across all 12 outdoor runs the classified distances (`runningDistanceMeters` + `walkingDistanceMeters` + `unclassifiedDistanceMeters`) fell **7–25 % short of the run's logged distance**, peaking at **1176 m "covered while standing still"**, because step 7 discards a stopped segment's distance. The cause is that **Strava's two stop signals disagree with each other**: on one 32-minute run the `moving` stream marks **450 s** as stopped while Strava's own `moving_time` for the same activity excludes only **118 s**. Trusting the flag alone counted real walking as a pause, which both shrinks the moving-time denominator and inflates Løping%. So the flag over-reports *and* (per v2) under-reports, and neither signal is authoritative alone: **ground covered is necessary in every case**, and the flag or the gap length only says which kind of standstill it is. The permanent invariant now asserted in the port: **you cannot cover ground while stopped**, so the classified distances must add up to the whole run. Note this is a *classifier* rule only — `movingSeconds` still honours an explicit `moving:false` unconditionally, because that is what reproduces `moving_time`, and it was validated on **treadmill** runs where belt distance is clean by construction; outdoor GPS carries far more sub-0.5 m/s time than Strava excludes (≥318 s vs 118 s on the run above), which is exactly why the classifier needs the extra gate and the accounting does not. **Outdoor-only, never fabricated** — a missing/short stream leaves the field absent. Powers the per-run detail breakdown + the dashboard Run/walk ratio trend; not used in any training-load computation. |
| `stravaAnalysis.aerobic` | object? | **Derived HR-drift + cadence estimate** for ANY Strava-linked run (indoor + outdoor — reads the HR sensor + accelerometer, not GPS). Auto-computed from the same streams as continuity: `decouplingPercent` (aerobic decoupling — first-half vs second-half speed÷HR over moving time, %; positive = HR crept up relative to pace, lower/negative = more durable; `hasDecoupling` false if no HR/speed or under ~10 min) and `avgCadenceSpm` (mean steps/min; Strava's per-leg stream is doubled below 120; `hasCadence` false if no cadence). **Version 2 excluded zero-speed samples** (`v > 0`, not `v >= 0`) — speed÷HR is meaningless while standing still, and such a sample adds nothing to the speed sum but its full weight to the HR sum. **Version 3 was the one that actually fixed it**: it reads the `distance` stream and shares **`movingSeconds`** with the splits analysis, because a real pause is a *time gap* rather than a stretch of zero-speed samples (see that field's row for the full shape). The 31.07.2026 tempo session, which contains a 219 s stop, reported **+24.1 %** under both v1 and v2 and **+7.8 %** under v3 — and its `movingTimeSeconds` stopped overshooting Strava's own `moving_time` by exactly the gap. **Walking still counts** — a walk break is part of the effort, a paused belt is not. **Deliberate, decided 2026-07-31:** a stop is deducted but does **not** disqualify the stretch. Strict continuity was considered and rejected because 🏃 Ute comes from Strava's `best_efforts`, which behaves this way (as do Garmin and TrainingPeaks — auto-pause simply never records the stopped seconds), and **both columns must play by the same rules** or the rebuild re-introduces the very asymmetry it removed. **Estimate, not truth** — decoupling is noisy on runs with walk breaks or hills (cleanest on continuous easy/steady), and indoor runs drift hotter, so compare indoor-vs-indoor / outdoor-vs-outdoor. **Cadence validated against Strava** (matches within ~1 spm both venues). Version-stamped (`version`), re-computed on algorithm bump; a missing stream leaves that metric absent, never fabricated. Powers the per-run "HR-drift & kadens" detail block; not used in any training-load computation. |
| `stravaAnalysis.splits` | object? | **Derived best splits inside a TREADMILL run** (absent otherwise). `best` maps a distance key → `{ t, startSec }`: the fastest **continuous** stretch at that distance anywhere in the run, plus how far into the run it began. This is the indoor equivalent of Strava's `best_efforts`, which Strava computes for outdoor GPS runs and **never** indoors — without it ⚙️ Inne could only ever offer whole runs while 🏃 Ute got true segments. **A measurement, not an estimate**: no classification and no smoothing, because Runna records treadmill runs from the belt speed the user types in, so distance matches the treadmill by construction and the speed profile is piecewise-constant. **Never scaled to the session's logged distance** — on an interval session the logged distance is *lower* than what was run (recovery jogs sit outside the plan's headline number), so scaling would compress a genuinely longer run and make every split artificially fast. The logged distance is used only to **reject** a run, never to rescale one: if the stream disagrees with `distanse` by more than **3 %** the run is measuring itself with a different ruler, and the result comes back `best: {}` with `distanceMismatch: true`. That guard is not theoretical — the ~20-25 pre-Runna Apple Workouts treadmill runs recorded *wrist* distance rather than belt distance and over-measure by up to ~18 %, and the "link old runs to Strava" backfill is what made exactly those analysable. The 5K test of 28.11.2025 (belt 5.00 km in 33:46) produced a "5 km split" of **28:41 — five minutes faster than the whole run it came from** — and took the ⚙️ Inne PR until `SPLITS_ANALYSIS_VERSION` 2 rejected it. **Second gate, `SPLITS_ANALYSIS_VERSION` 3 — the run must carry a cadence stream.** The distance check only catches a run that disagrees with *itself*, and across the whole history that is **one run**: 51 of 52 treadmill runs agree to ±0.7 %, because the logged distance was imported from the same watch that recorded the stream. **Agreement proves consistency, not correctness.** The pre-Runna era is identified instead by what it lacks: **24 consecutive runs (2025-10-02 → 2026-03-12) have no cadence stream** — matching the user's own "maybe 20-25 runs that used apple workout app only" — and every run from 2026-03-16 has one. Cadence is per-run evidence of *how the run was recorded*, so a stray day logged without Runna (2026-04-17) is excluded on its own merits rather than by a calendar cutoff. Detected with the **same moving-aware test as `analyzeAerobicMetrics`**, deliberately duplicated so the two can never drift on what "has cadence" means; sets `noCadence: true`. A rejected run is stored as a **valid empty result**, not `insufficientData`, so it stamps current and is never re-fetched. **Version 4 fixed the window arithmetic itself.** The overshoot is trimmed at the **start** of the window, not the end: the sliding loop advances `start` as far as it legally can, so the excess distance sits in the *first* segment (the exit condition `dist[end]-dist[start+1] < need` proves `over < firstSeg`). v1–v3 converted that overshoot at the *last* segment's pace, which silently under-counts time whenever a window starts fast and ends slow — i.e. on **every interval session**. It reported a **400 m of 1:29 on a belt that never exceeded ~13 km/h** (physical floor 1:51), having charged ~40 m of rep-pace overshoot at walking pace. Constant pace hides the bug entirely, because both segments share one pace — which is why 51 synthetic tests ran straight past it. The permanent invariant now asserted in the port: **no split may be faster than that distance run at the fastest speed the belt ever reached.** **Version 5 put splits on the moving clock.** `t` is measured over cumulative **moving** time via the shared **`movingSeconds(time, dist, moving, i)`** (used by the aerobic analysis too, so the two cannot disagree about what counts as running time). **A real pause is a time GAP, not a run of stopped samples** — this took three attempts to get right. Dumping the actual streams showed `exactly flat: 0 s`: a pause is a single ordinary sample pair whose clock jumps while the distance **creeps 0.5–3.3 m**, with no sample inside it. Strava's `moving` stream does not flag them, the distance is never exactly flat, and `velocity_smooth` reports the normal running speed of the samples either side — so testing for a `moving` flag, flat distance, or zero speed all failed. The rule that works: an interval counts only if it covered ground at **≥ `MIN_MOVING_SPEED_MS` (0.5 m/s)**, with an explicit `moving:false` still honoured and a raw-elapsed fallback when there is no distance stream. **Validated against external ground truth:** dropping sub-0.5 m/s intervals reproduces Strava's own `moving_time` to within a second on both test runs (3688−69 = 3619 vs 3620 logged; 2610−257 = 2353 vs 2353 logged). Measured gaps: three totalling 69 s in the 11.07 10K test, and 257 s in the 31.07 tempo run including one of 219 s spent retrieving a dropped AirPod. Implied speeds inside them run 0.006–0.28 m/s against ~2.4 m/s running and ~1.1 m/s walking, so the threshold sits an order of magnitude clear of anything real. Walking still counts — a walk break is part of the effort, a paused belt isn't. This matters because a session's `varighet` *is* Strava's `moving_time` and the ⚙️ Inne column shows split times and whole-run times in the same table. On the elapsed clock the 10K test reported a best 5 km of **6:07/km inside a run averaging 6:02/km** — the better half reading slower than the whole, purely because ~50 s of stopped belt fell inside the window. `startSec` deliberately stays on the **elapsed** clock: it locates the stretch for scrubbing in Strava, it is not a duration. Second permanent invariant: **the best window over distance D cannot exceed `totalMovingTime / floor(L/D)`**, since that many disjoint windows tile the run and their times sum to at most the total. A distance the run never reached is simply absent — never zero. Version-stamped; feeds the ⚙️ Inne column and the per-run "Beste splits" detail block, **and both read it version-gated** — a superseded analysis may hold a value the current rules would refuse to produce. |

## Belt vs GPS — never merge these

- **Treadmill PRs** are belt-measured. **Strava best efforts** are GPS-measured, outdoor-only (Strava computes no best efforts for treadmill runs).
- Outdoor pace at the same HR reads consistently faster than treadmill — likely belt calibration, GPS error, and indoor heat/airflow. Treat the surfaces as separate populations; do not combine belt and GPS times in one ranking.
- **The 1 % convention covers still air, not terrain.** It compensates for the missing wind resistance indoors; it does nothing for hills. Outdoor runs carry real elevation while a treadmill is flat by definition, so that is an uncompensated outdoor penalty on top of everything above.
- **The two effects pull in opposite directions, and the net is not measurable from this dataset.** Ideal indoor conditions (flat, still, climate-controlled) should make belt times faster; the observed same-HR data says outdoor is faster. Any apparent gap between a belt PR and a GPS PR here is mostly **effort**, not surface — e.g. a maximal treadmill 10K test vs a 10 km stretch inside an easy outdoor run. Until there is a maximal effort in *both* venues, a belt↔GPS offset cannot be derived, only guessed. This is the real reason the two are never merged: not "one is faster", but "these are not commensurable and nothing logged says by how much or which way".
- **This rule is now enforced in the UI** (2026-07-31). Distanse-PR renders one row per distance with two independent columns — 🏃 **Ute** (Strava best effort) and ⚙️ **Inne** (treadmill) — and nothing merges them. The previous blended value (whichever of belt/GPS was faster, under a venue-neutral "Faktisk tid" label) is gone; because belt reads faster it had silently become the treadmill number for most distances.

## Distance PRs (`computeDistancePRs`)

Single source of truth for the Rekorder card **and** the "Ny …-PR!" insight, so the two can't drift.

- **Ute** = `bestEffortsTop3[key][0]` — Strava's best effort, i.e. the fastest stretch at that distance **inside any outdoor run**. Segments count: a 5 km PB run inside a 10 km run is a 5 km PB. Only `[0]` is shown — the runners-up are stored but **not rendered anywhere** (see `bestEffortsTop3`).
- **Inne** = the **fastest** of three sources, each carrying a `source` so the cell can say how exact it is:
  - `split` — the fastest continuous stretch at that distance inside any treadmill run, from `stravaAnalysis.splits`. **Exact distance**, so this is the indoor equivalent of Ute. Cell shows the date alone.
  - `run` — a whole `løpetype: 'treadmill'` session within **±2 %** of the distance. Approximate, so the cell also shows the run's real distance.
  - `manual` — hand-entered in Innstillinger. **No date**, so it can never fire the fresh-PR insight or anchor Prognose. Since splits landed this is a **fallback only** — for sessions the app cannot see (a gym treadmill never uploaded, or a run with no `stravaId`). It is *not* the normal way treadmill PRs arrive any more.
- **The ±2 % window is what keeps the label honest.** The old ±10 % bracket accepted 4.5–5.5 km as "5 km", picked by best *pace*, then printed the run's *total duration* — so a 5.41 km run displayed as `5 km · 0:34:17`. An **empty cell is the correct answer** when nothing qualifies; a wrong number is not.
- `utenforAnalyse` sessions are excluded (consistent with all other quality records).
- **The asymmetry is now closed** (2026-07-31): both columns are segment-based — Ute from Strava's `best_efforts`, Inne from `stravaAnalysis.splits` derived here. A whole-run or manual value only fills in where no split exists (an unlinked run, a gym session never uploaded, or a pre-Runna recording whose stream failed the 3 % distance-agreement guard). The columns remain **separate populations** and are still not meant to be compared to each other.

## Prognose (`computePerfCurve`)

Riegel projections **only** for distances with no actual time in *either* column — anything real lives in Distanse-PR, so the two sections can never show competing numbers for the same distance.

- **Two independent columns, each anchored in its own venue.** 🏃 Ute answers "what could I race?", ⚙️ Inne answers "what am I capable of on the belt?". Each prefers a **maximal** effort (`Test`/`Race` ≥3 km) in that venue and falls back to the measured PR there. Never blended.
- **Why Inne exists at all:** roughly half the year every run is indoors. An outdoor-only projection sits frozen on last season's efforts through the whole winter while the actual fitness change happens on a treadmill — least informative exactly when it's most wanted.
- **`INNE_MAX_PROGNOSE_KM = 21.1`** — no indoor projection beyond a half marathon; a treadmill marathon estimate has no use. That cell renders **blank**, not `–` (a dash means "not run yet" in Distanse-PR; this is "not applicable").
- **Riegel degrades past ~3× the anchor distance.** From a 10 km anchor, 15 km (1.5×) and half (2.1×) are sound; the marathon (4.2×) is not, and when its anchor is also non-maximal it is the softest number on the card. The section caption carries this caveat — **deliberately no per-cell confidence badge**.
- **Anchors are named once per section, not per row** (`fra 10 km inne (11.07.2026)`). In winter this is what makes a months-old outdoor anchor obvious next to a current indoor one. If a column ends up using more than one anchor it says "nærmeste distanse" instead.

## Events (`Store.data.events`)

`{ id, date, type, endDate?, title }` — types: `plan`, `race`, `illness`, `vacation`, `deload`, `taper`, `personal`. `endDate` is **inclusive**. Plan events may carry `targetTotalKm` / `targetKmPerWeek` / `targetRunsPerWeek`; race events may carry `distanceKm` (optional — absent behaves exactly as before).
Which fields the form shows is decided in **one** place, `Settings.syncEventFields()` (modelled on `Form.syncVenueFields`): plan → the three targets, race → `distanceKm` **and no `endDate`** (a race is one day), everything else → neither. It **empties what it hides**, so a value you can't see can never reach `addEvent`. Called from the type-change handler, `editEvent`, `_clearEventForm` **and init** — the missing init call is why the form used to open showing "Plan" with its targets hidden.
`distanceKm` is read by the race countdown insight, by **Løp & Races** (an upcoming race shows its distance where the stats line was blank), in the **Hendelser row itself** (in the space a race's missing `endDate` leaves — trailing zeros stripped, so `5` renders "5 km"), and to pick the *closest* nearby run rather than the *longest* when no `Race`-typed session exists. That last one is the reason it is worth filling in even when the title already says "5K": it is the only thing steering which logged run gets matched to the race.
Syk/Ferie/Deload/Taper events **explain gaps and dips in the volume charts** — check them before interpreting a drop as detraining. Treningsrytme treats runless weeks covered by `illness`/`vacation` as unavailable rather than failed.

## Other data stores

- `bestEfforts` — **removed 2026-08-05. Nothing reads it.** Hand-entered treadmill best-effort times (seconds) per distance, previously under Innstillinger → *Tredemølle-PR*, feeding the ⚙️ Inne column when they beat a logged belt run. Dropped because both remaining Inne sources (`split`, `run` — see below) are automatic and dated, and cover every case the field claimed: a run without a Strava link still qualifies via `run`, and one that was never logged at all has no business showing a PR. It was also actively hazardous — the value stayed in the store after being beaten, so it would silently resurface as the PR whenever a faster derived value dropped out (a `SPLITS_ANALYSIS_VERSION` bump, an unlink, a deleted run), defeating the version gate whose purpose is an empty cell over a wrong number. Being dateless, it could also never anchor Prognose or fire the fresh-PR insight. **Existing values are deliberately left in place**, not deleted: `Store.toJSON()` serialises `Store.data` wholesale, so they keep round-tripping untouched and a revert would restore them. (Earlier, 2026-07-31: the store had been a belt/GPS *blend* via the "Bruk / Bruk alle" review — deleted then, outdoor moved to `bestEffortsTop3`. Values predating that may still hold outdoor times, which is now moot.)
- **⚙️ Inne in Distanse-PR has two sources**, fastest wins, each carrying its `source` so the cell can state its precision: `split` — the fastest continuous stretch at the distance inside an **analysed** treadmill run, derived from the Strava streams and **version-gated** on `SPLITS_ANALYSIS_VERSION` (a superseded analysis is refused outright; an empty cell beats a number the current rules would reject); `run` — a whole treadmill run within **±2 %** of the distance, so the cell shows that run's real distance beside the date. Both are dated. Neither ever draws on outdoor runs — see "Belt vs GPS".
- `bestEffortsTop3` — Strava-scanned top-3 per distance `{t, d}`; GPS/outdoor only. **Its #1 is the 🏃 Ute column** in Distanse-PR. **#2/#3 are stored but render nowhere** — the "Topp 3 utendørs" expander that showed them was deleted 2026-07-31 (`d43ee20`: noisy, and Strava shows the same list anyway). They are kept deliberately, because the parked "how much did I beat my old PB by" work needs that history — **don't remove the collection as dead weight.** Ranked by **time, not chronology** — the runner-up is not "the previous PB" and must never be read as one. The scan's `localStorage` buffer is **device-local** (not Drive-synced); only this committed field syncs. Commits **merge** (union, dedupe on `(t,d)`, fastest 3) into the existing set — never overwrite — so a sync on one device can't drop history scanned on another. Refreshed only when you click *Synkroniser fra Strava*. Rebuild a depleted set via Innstillinger → "Skann hele historikken på nytt".
- `shoes` — `{ name, retirementKm?, retired?, obtained? }`. `obtained` = purchase month `YYYY-MM` (picked via **two dropdowns** month+year — cross-browser, unlike a native `<input type=month>`); drives the shoe's displayed **age** on its Innstillinger card. Editable on existing shoes via the card's Rediger panel. A malformed value (won't happen via the dropdowns) just renders no age.
- `shoeDefaults` — `{ outdoor?, treadmill? }` (shoe *names*). The per-venue default that **pre-selects** `#fSko` on the log form (and swaps when løpetype toggles); always overridable per session, so it never constrains what's saved. Absent/blank = fall back to last-used shoe.
- `goals` — yearly km targets keyed by year.
- `continuitySettings` — `{ walkMaxKmh, runMinKmh }` walk/run speed thresholds (km/h) for the Run/walk ratio estimate; below `walkMaxKmh` = gange, above `runMinKmh` = løping, between = uklart. Absent = defaults **7.0 / 7.5** (calibrated on real runs). Changing them re-stamps stored analyses stale (re-run via the detail-view button or the Innstillinger backfill).
- `plannedSessions` — planned RUN sessions imported from a Runna training-plan `.ics` (Planlegging → Planlagte økter), for planned-vs-actual tracking. Each: `{ id, date, planWeek?, okttype, distance, title, sourceUrl? }`. **Import-derived, not hand-authored.** An import is **additive across blocks**: rows are scoped to the **active Plan-event block** (only dates ≥ the block's start, so old completed sessions in the `.ics` don't flood in), and the write then replaces **exactly the date range the import covers** — `[first, last]` — keeping every row outside it. No dedup pass is needed, since kept rows lie strictly outside that window and imported rows strictly inside, so re-importing the *same* block is still a clean replace of that block. **The range must come from the import, never from the active block:** anchoring it on `active.date` wiped the *current* block whenever you imported the **next** block's plan before the current one ended, even though the import touched none of its dates. Before 2026-08-08 the import overwrote the whole array, which **silently destroyed every finished block's planned-vs-actual record**: `plannedForBlock` still window-bounded correctly, the rows were simply gone. Because the store now spans every block, the **Planlegging card scopes to the active one** (falling back to all rows when no Plan event covers today, so it doesn't empty out between blocks) and `clearPlanned`'s confirm names the full count, since what it destroys is no longer all visible above it. Runs only: strength (🏋️, no km) and ad-hoc completed runs (`COMPLETED_NON_PLAN_WORKOUT`) are skipped; **completed** plan days (`COMPLETED_PLAN_WORKOUT`) are kept so a mid-block import still shows done sessions. Matched to `sessions` at **render time** (ISO-week bucket + nearest date + type, run-only if done on/after the planned day — no stored match state). Surfaced in the Planlegging card, the active Treningsblokker hero (adherence bar + next-up), and the block detail panel. Not used in any computation. Parser/UID-format details in HANDOFF.
- `countryNotes` — free-text memory per country `{ ISO: text }` (e.g. `{ "PH": "treadmill was in mph…" }`). The **one user-authored/persisted** Løpeatlas piece (everything else is derived); text only, no media. Edited/shown in the country drill-down (`DetailPanel.openLand`); a 📝 dot marks chips that have one. Absent = none; empty save deletes the key. Not used in any computation.
- **Løpeatlas** (travel stats + **42 fixed achievements** in 6 groups Milepæler/Land/Verdensdeler/Distanse/Omgivelser/Sesong, **plus dynamic per-year New Country Year stamps** — so the badge total grows over time) is **fully derived** from `sessions` (`land`/`dato`/`distanse`/`løpetype`/`okttype`/`hoydeMeter`) + `events` (`vacation` overlap for the Vacation Runner badge) via `computeAtlas()` — **nothing persisted**, no badge state, so editing an old run's date/country can shift derived unlock dates ("Sist låst opp"). Home = `ATLAS_HOME='NO'`; blank `land` = home. Country-collection tier badges (Passport/World Traveler/Frequent Flyer/Globetrotter) count foreign countries only; regional-explorer + continents + Nordic count all resolved incl. home via the static `CONTINENTS` map (6 inhabited; Antarctica excluded; Both Hemispheres uses a `SOUTHERN` hand-list); unresolvable `land` text still shows as a chip but has no continent. The two **Nordic** badges live under Verdensdeler (a near-home European sub-region — no standalone Norden group). The **country drill-down** (`DetailPanel.openLand`, opened from a flag chip) shows a **"Teller mot"** list — which badges that country counts toward (`atlasBadgesForCountry`): the collection/continent/regional/Nordic sets it's a member of, plus anything unlocked *there*; aggregate/temporal badges like the globe-km ladder appear only when unlocked there. Three states: **gold ✓ = låst opp her** (this country's run earned it, `b.country === code`), **green ✓ = låst opp** (done, this country counts but another tipped it), **grey tally = gjenstår** (in progress). A small legend keys only the two checkmark colors (`✓ låst opp i <land> · ✓ låst opp`, the country name interpolated for clarity) — the tally is self-explanatory. Conversely, clicking a **badge** in the atlas grid opens its own drill-down (`DetailPanel.openBadge`): status, the full **ladder progression** for laddered badges (`Nivåer` — every tier with ✓/tally, current one highlighted), and the **countries/continents that count toward it** (`atlasBadgeContext` — clickable chips through to each country). The two surfaces are inverses: country → badges, badge → countries. Tiered **ladders** (`ATLAS_LADDERS`: foreign-country count, continents, Nordic, longest-single-run distance, cumulative km abroad `globe-*` 10→25→50→100→250, distinct outdoor-abroad countries `outdoor-*` 3→5→10, and single-run elevation gain abroad `hills`/`foreign-climber`/`foreign-summit` 50→200→500 m) show unlocked tiers + only the next locked one, so a beginner starts on an obtainable target that escalates once reached. Elevation tiers are **per single run** (the hilliest one foreign outdoor run), not cumulative — 500 m is a deliberate mountain-trip stretch. A few badges carry **dynamic** names/desc from the derived data: Multi-Year Traveler lists the actual years (`… i 2 kalenderår: 2025, 2026`). **New Year, New Country** is a set of **dynamically generated per-year badges** (not one static badge; internal id `new-country-year-<YYYY>`): one permanent stamp `New Year, New Country (YYYY)` for each calendar year you first ran in a **brand-new foreign country** (first-ever run in that country falls in that year), showing the year + unlocking country (`Nytt land i 2026: Sverige +N` if several that year) + its flag; the **current year always appears too**, as a locked objective until you discover somewhere new (`Løp i et nytt land i 2026`). Built in `computeAtlas` (grouping `foreignByFirst` by first-run year) and appended to `a.badges` — so past years never un-earn (fixing the old single-badge annual reset). Single-run/threshold badges also carry the **country where they were earned** (`country` ISO code in the badge object) and render a small flag + country name on the "Låst opp" line; continent-count (Continental/Global), cumulative-km (`globe-*`), Multi-Year, and New Country Year (already named in its desc) deliberately carry no flag.

## Durability rules (how the data is protected)

- **An edit merges, it does not replace.** Saving from the log form updates only the fields the form
  owns; anything else on the session (notably `stravaAnalysis`, and any legacy field like `sovn`)
  survives untouched. Fields the user deliberately clears still clear. Before 2026-07-30 an edit
  rebuilt the session from form fields alone and silently dropped everything else.
- **A save reports honestly.** `FileIO.save()` returns whether the data actually reached durable
  storage. A failed write shows a persistent red sync state plus a message — never "Lagret". Bulk
  operations check this and won't claim success (or spend Strava API calls) on unsaved state.
- **Bulk writes snapshot first.** Linking old sessions to Strava and the analyse-all backfill both
  write a `BackupDB` snapshot before mutating, like the Slett-alle button — recoverable from
  Innstillinger → Lokale sikkerhetskopier (daily, last 7).
- **A load must look like a dataset.** `Store.load()` validates the parsed shape *before* adopting
  it; a JSON array, `null`, or a primitive is rejected with the existing data left intact. (Such a
  file used to be adopted wholesale and then serialised back as `[]`, wiping the real data.)
- **`pulsDrivePendingLocal`** (localStorage, device-local) — set whenever a Drive save doesn't
  succeed, including offline. Persisted deliberately: if it were memory-only, a failed save followed
  by a reload would let Drive's older copy overwrite the unsaved edits. While set, the next load
  routes into the conflict prompt instead of applying Drive's copy.

## Computation conventions

- Riegel exponent **1.06** for all equivalent-time math (`t2 = t1 × (d2/d1)^1.06`).
- Zone-weighted load = `Σ(soner[i] × [1,2,3,4,5]) / 60` (weighted minutes). PMC: CTL 42-day / ATL 7-day exponential averages of daily load; TSB = CTL − ATL.
- All "today"/window boundaries use local dates, never UTC.
